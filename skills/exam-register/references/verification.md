# 검증과 완료 판정

입력 명세와 저장값의 일치만으로 원본 형식 일치를 판정하지 않는다. 명세 자체가 원본·사용자 지정 구조와 맞는지도 검사한다. 별도 지문은 general_document 여부, 문항과의 분리, 안내 머리글의 박스 밖 위치, 원본 박스 및 박스 제목 유무, `(가)·(나)`와 내부 문단·강조를 확인한다. 박스가 필요한 원본에 대해 `fieldset 없음`을 성공 조건으로 두지 않는다.

MCP 기능 검증은 생성·입력·서식·재조회별 성공과 제약을 보고한다. 사용자 범위가 MCP 검증이면 브라우저 작업을 추가하지 않는다. 이 경우 저장 구조 검증 성공과 실제 UI 미검증을 구별하고 전체 시각 검증 완료로 표시하지 않는다.

문단 서식 검증은 원본 관찰 → 서식 계획 → MCP 저장 속성을 문단별로 대조한다. 본문·대화·시·중략 안내·작품명·출처가 섞인 지문에서는 각 역할의 들여쓰기 유무·크기, 정렬, 행갈이 차이가 유지되는지 확인한다. 첫 줄 1자 들여쓰기·양끝 정렬을 모든 문단에 일괄 적용한 결과를 성공으로 판정하지 않는다. 특정 문항에만 요청된 서식은 다른 문항에 전파되지 않아야 한다. 미확인·미지원 문단을 성공 항목으로 집계하지 않는다.

검토 사례: 원본에서 본문은 들여쓰기·양끝 정렬, 시는 별도 행갈이·왼쪽 정렬, 출처는 오른쪽 정렬로 확인된 경우 각각 보존한다. 이는 사례의 원본 조건이며 역할별 고정 서식 규칙이 아니다. 사용자가 한 본문 문단만 첫 줄 1자로 바꾸라고 요청하면 그 문단만 변경하고 나머지는 원본 기준을 유지한다. 저장 속성 검사만 수행했다면 실제 렌더 재현까지 확인했다고 보고하지 않는다.

source: 원본 ↔ 전사·크롭. structure: 명세 ↔ 저장 내용·정답·이미지 참조 — `item_read {format:"html"}` 응답을 파일로 저장하고 `scripts/check_readback.py <question.json> --read <응답.json> --workspace <root>` 로 발문·선택지 순서와 문구·정답 체크·이미지 assetId·밑줄·보기박스 개수와 제목을 대조한다. 보기박스 제목은 요소의 `viewbox_title`(null = 제목 없음)로 명세한다. 도구가 못 보는 것(수식 LaTeX · 표 셀 · 문단 서식 속성)은 read 의 outline/json 으로 수동 대조하고 그 항목을 notes 에 적는다. visual: 원본 ↔ 실제 편집기 화면.
각 단계는 pending/passed/failed/unavailable, 증거 파일 경로와 검토자를 기록한다. visual=passed 에는 실제 화면 캡처 파일(`runs/<id>/verification/<qid>-screen-<n>.png`)이 증거에 있어야 하며 `check_manifest.py` 가 이를 검사한다. 브라우저 도구가 파일 저장을 지원하지 않아 캡처를 대화 안에서만 관찰했다면 visual 은 `unavailable` 로 두고 `notes` 에 그 사실을 적는다 — passed 로 올리지 않는다. 에이전트 검토를 사람 검토로 표시하지 않는다. 질문·선택지·숫자·부정 표현·밑줄·테두리·수식·순서·공통 지문을 확인한다.
기계적 검사는 스키마·중복 ID·좌표·파일·해시·참조·상태만 다룬다. 의미·원문 전사·크롭 품질을 보장하지 않는다. 경계가 이미지 안에 있다는 사실은 자료 전체가 들어 있다는 뜻이 아니다.
verified 조건: 세 검증 모두 passed + 증거 파일 + 문서 ID + 미해결 issues 없음 + 필요한 정답/배점 적용 완료. 화면 도구가 없으면 visual=unavailable, state=registered 또는 blocked이며 verified는 불가다.
대표 사례는 이미지 자료, 텍스트 보기, 연표, 복합 편지다. 실패 사례는 잘못된 좌표, 업로드 실패, 응답 손실, 버전 충돌, 재개 중복 방지, 화면 미확인이다. 장애 주입은 로컬 모의 자료 또는 이번 검증 전용 문서로 한정한다.
시간은 render/extract/upload/register/verify로 나눠 기록한다. 검증을 생략해 줄인 시간을 개선으로 세지 않는다.
